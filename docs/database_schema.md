# Database schema and data management

## Database stack

New installations use PostgreSQL, SQLAlchemy 2 ORM models in `backend/app/models.py`, and versioned Alembic migrations under `backend/alembic/`. `DATABASE_URL` selects the PostgreSQL database. The API applies pending migrations at startup; the deployment procedure also runs `python -m alembic upgrade head` explicitly before service start. The initial migration creates 24 tables with primary keys, foreign keys, uniqueness rules, checks, and time/status indexes.

For compatibility, setting only the legacy `DATABASE_PATH` opens the existing SQLite database through SQLAlchemy's SQLite dialect and retains its additive bootstrap. PostgreSQL is the supported new-installation and production target.

## Entity groups

| Group | Tables | Purpose |
| --- | --- | --- |
| Identity and policy | `users`, `sessions`, `app_config`, `audit_logs` | Password hashes, hashed expiring sessions, thresholds and accountable changes |
| Telemetry | `system_metrics`, `processes`, `services`, `service_snapshots`, `service_dependencies`, `logs` | Timestamped host observations, inventory, typed edges and journal records |
| Intelligence | `anomaly_findings`, `predictions`, `model_versions`, `evaluation_runs`, `root_cause_findings`, `recommendations` | Explainable signals, model metadata, chronological evaluation and operator guidance |
| Safety and operations | `impact_assessments`, `risk_assessments`, `actions`, `approvals`, `incident_actions` | Persisted risk/impact, bounded requests, decisions and linked actions |
| Incidents | `alerts`, `incidents` | Deduplicated alerts and their investigation lifecycle |
| Runtime | `collector_state` | Collector health and observation counters |

IDs are generated by PostgreSQL identity/serial columns. JSON evidence is stored as text for portable API serialization. Foreign keys connect users to sessions/audit/policy changes, metrics to anomalies, alerts to incidents, and actions/approvals/impact/risk records to their actors and related incidents. Unique keys prevent duplicate users, incident keys, recommendation keys, model versions, dependency edges, service snapshots, journal cursors, and anomaly-method findings per observation.

## Migrations

From the `backend` directory, configure `DATABASE_URL` in the root `.env`, then run:

```bash
python -m alembic upgrade head
python -m alembic current
```

Create future reviewed revisions with `python -m alembic revision --autogenerate -m "describe change"`; inspect the generated migration before applying it. Do not edit a migration already applied to a deployment.

## Move an existing SQLite installation

Back up the source SQLite file, start a new empty PostgreSQL target, and set both `SOURCE_SQLITE_PATH` and `DATABASE_URL`. Then run:

```bash
python scripts/migrate_sqlite_to_postgres.py
```

The migration script reads SQLite in read-only mode, copies only columns present in both schemas, preserves IDs, restores PostgreSQL sequences, and aborts if the target contains rows. Retain the source until the API, metrics, users, actions and incidents have been checked against PostgreSQL.

## Backup and restore

Use a protected PostgreSQL service account and a consistent dump:

```bash
pg_dump --format=custom --file=platform.dump "$DATABASE_URL"
createdb linux_admin_restore_test
pg_restore --dbname="$RESTORE_DATABASE_URL" platform.dump
```

Keep backup credentials out of shell history and logs. Test a restore in a separate database, then verify health, recent metrics, users, actions and incident history. Coordinate retention with backup retention; metric/process/service/log/prediction history follows `RETENTION_DAYS`, while audit and incident history is retained for accountability.
